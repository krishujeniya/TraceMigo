# ADR 0005: Content publication and private bundle projection isolation

- **Status**: ACCEPTED
- **Date**: 2026-10-26
- **Accountable Owner**: SECURITY (TraceMigo Trust & Isolation)
- **Reviewers**: ENG, CONTENT
- **Traceability**: REQ-P-03, REQ-P-07, Audit A09

## Context and Problem Statement

The initial database schema draft stored `private_bundle_key` alongside `public_manifest_key` on the main `problem_versions` table. Concurrently, the security architecture mandated that learner-facing web and API processes must have zero access to private ground truth, hidden test suites, or oracle solutions.

Relying solely on application-level serialization filters (e.g. stripping keys before API response rendering) is fundamentally flawed:
1. ORM/query changes or logging middleware can inadvertently leak private storage keys.
2. Compromise of the web application container would yield direct database access to all private bundle locations and sealed evaluation fixtures.

## Decision

We enforce defense-in-depth separation across **Database Schema**, **Database Roles**, and **Cloud Storage Buckets**:

### 1. Database Table Separation
We split public metadata from private evaluation authority:
```sql
-- Accessible by web application and public API
CREATE TABLE problem_versions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    problem_id UUID NOT NULL REFERENCES problems(id),
    version_number INTEGER NOT NULL,
    status publication_status NOT NULL DEFAULT 'draft',
    content_hash VARCHAR(64) NOT NULL, -- SHA-256 of public manifest
    public_manifest_key VARCHAR(512) NOT NULL,
    published_at TIMESTAMPTZ,
    UNIQUE (problem_id, version_number)
);

-- RESTRICTED: Accessible only by isolated judge orchestration
CREATE TABLE problem_authorities (
    version_id UUID PRIMARY KEY REFERENCES problem_versions(id) ON DELETE CASCADE,
    private_bundle_key VARCHAR(512) NOT NULL,
    oracle_hash VARCHAR(64) NOT NULL, -- SHA-256 of private oracle
    witness_hash VARCHAR(64) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
```

### 2. Database Privilege Boundaries
- `tracemigo_app_role` (used by `apps/web` and user-facing APIs):
  - `GRANT SELECT` on `problem_versions`, `problems`, `problem_tags`.
  - `REVOKE ALL` on `problem_authorities`.
- `tracemigo_judge_role` (used strictly by `services/judge-controller`):
  - `GRANT SELECT` on `problem_authorities` and `problem_versions`.
- Connection pooling configurations ensure no pooled connection is shared across these distinct roles.

### 3. Object Storage Isolation
- **Public/Learner Bucket** (`tracemigo-public-content`): Contains starter files, readme, and public manifests. Accessible via short-lived signed URLs generated by the API.
- **Sealed Evaluation Bucket** (`tracemigo-sealed-content`): Contains secret test cases, regression witnesses, and oracle implementations. Encrypted with a customer-managed KMS key. Google Cloud IAM strictly limits read access to the Judge Controller workload identity. Web application service accounts have zero IAM permissions on this bucket.

### 4. Immutable Publication Protocol
Once published, a problem version is permanently immutable:
- `content_hash` and `oracle_hash` guarantee integrity.
- Any correction, typo fix, or rubric update requires creating a new version (`version_number + 1`) requiring two independent content reviews before publication.
- Prior versions remain readable for historical attempt auditing.

## Consequences

- **Positive**: Complete architectural defense against ground-truth leakage; web container compromise cannot read sealed assessment or oracle files; audits can mathematically prove access denial.
- **Negative**: Requires managing two distinct database connection pools/roles; content publication pipelines must orchestrate dual-bucket uploads.
